# 版本线与双线并行管理方案

> 建立于 2026-10-28（#51 事故后）。适用范围：`gyのFW` 全部分发线与开发线。
> 本方案解决两件事：**① 1.x/2.x/3.x 只发一部，互不夹带；② 部署线与开发线并行，互不阻塞。**

---

## 一、版本号 = 分发边界（硬规则）

主版本号即「包含哪几部」，不是营销号：

| 版本线 | 内容 | 服务器包 | 房间名 | 分发包产物 |
|---|---|---|---|---|
| `1.x.y` | **仅第一部** forest（48 关） | `gy-fw-forest-1.x.y.tar.gz` | `forest` | 有 |
| `2.x.y` | **仅第二部** light（40 关） | `gy-fw-light-2.x.y.tar.gz` | `light` | 有 |
| `3.x.y` | **仅第三部** ice（51 关） | `gy-fw-ice-3.x.y.tar.gz` | `ice` | 有 |
| `0.x.y` | 开发主线（三部同仓，无分发包） | — | 三部 | 无 |

规则：

1. **一个 tag 只对应一部**。`1.0.1` 打的包绝不含 light/ice 的关卡、图集、专属音频与音轨。
2. **主版本号切换 = 新分发线起点**。`2.0.0` 是第二部第一版，从 `main` 现况切出，不从 `1.x` 累积（避免继承第一部的剪裁假设）。
3. **同一部内只升次/修订号**（`1.0.1 → 1.0.2 → 1.1.0`）。跨部需求（如同时修三部的引擎 bug）走 `0.x` 主线并**回灌**到各分发线（见 §四）。
4. **`0.x` 永不发分发包**。它是开发主线，三部共存、全测试全跑。

> 为什么不用 `1.x` 同时容纳多部：一旦一个包里有两部，`/api/levels` 的分部断言、图集剪裁、房间名、部署验收的「只含某部」检查全部退化成模糊判断。1.0.0 的验收盲区已证明含糊的边界会漏缺陷。

## 二、分支模型（三条线并行）

```
main                              ← 开发主线（0.x）：三部同仓，全测试
├─ release/1.0-forest             ← 第一部部署线（1.x）：main 的子集 + 剪裁
│                                   只接受：从 main 回灌的引擎/安全/保真修复
├─ release/2.0-light              ← 第二部部署线（2.x）：2.0.0 时从 main 切出
│                                   2.x 未开工前不存在；不要在 1.x 上提前开
└─ release/3.0-ice                ← 第三部部署线（3.x）：3.0.0 时切出
```

核心约定：

- **main 是唯一真相源**。所有开发（含为某一部做的改）都先落 main，再回灌分发线。
- **分发线只做剪裁 + 打包链维护**，不直接改业务逻辑。分发线上出现业务改动 = 流程错误。
- **分发线必须定期跟随 main**。触发点：`drift-check` 作业每周检查，若 `release/*` 落后 main 超过 20 个提交或闲置超过 7 天，标 DRIFT 告警（见 §五）。
- 分支名带主版本号，便于机器判断该线该发哪一部。

## 三、两条并行线怎么分工

你提到的两条线，本质是**不同关注点、同一代码库**：

| | 开发线（`main`，0.x） | 部署线（`release/<部>-<n>.x`） |
|---|---|---|
| 目标 | 继续做后面几部、玩法/保真/性能 | 让某一部稳定跑在服务器上 |
| 频率 | 每天多次提交 | 只在「需要更新服务器」时切版本 |
| 覆盖面 | 三部全测试 + determinism 三锚 | 单部测试 + 单部 det 锚 + 部署冒烟 |
| 谁触发 | 开发需求 | 部署需求（用户说「更新服务器」时） |
| 失败代价 | 只影响开发 | 影响线上玩家 → 必须过全验收 |

**并行规则**：

1. 开发线的破坏性改动**不得直接推分发线**。要走「main → 验证 → 回灌」。
2. 分发线修的线上 P0（如 #51）**必须立刻回灌 main**，否则下次切部分支会重现。
3. 两条线各自独立发版：`1.x.y` 与 `0.x.y` 可以同一天各发一个，互不等待。

## 四、跨线回灌流程（本次 #51 就是这个流程缺位）

```
main ──修 bug──► 落 main（0.x 测试全绿）
                    │
                    ├─► cherry-pick / merge 到 release/1.0-forest
                    │      │
                    │      └─► 剪裁适配（测试/CI 作业/打包清单）
                    │           │
                    │           └─► 单部门禁 + 部署冒烟全绿 ──► 发 1.x.y
                    │
                    └─► 同步到 release/2.0-light（若已存在）
```

**必须回灌的内容**（缺一即视为缺陷）：

- 引擎/物理/机关修复（影响所有部）
- 安全修复（CSP、鉴权、限流、Origin）
- 协议/状态 schema 变更（客户端与服务端必须同版本）
- 打包链与验收脚本本身的修复

**只在单部生效的改动**（不必回灌）：该部专属关卡数据、图集、音轨、路线语料。

**回灌检查表**（每次 cut 版本前逐条过）：

- [ ] `git log --oneline release/X..main` 逐条看过，分类「该灌/不该灌」
- [ ] 该灌的全灌完；不该灌的在发版注记里写明理由
- [ ] 分发线 `npm test` 绿（剪裁后的测试集）
- [ ] 分发线 determinism 单部锚一致
- [ ] 打包 + 部署冒烟绿

## 五、机器可验证的护栏（防 #51 重演）

| 护栏 | 位置 | 违约后果 |
|---|---|---|
| 分发线漂移告警 | CI `drift-check`：`main` 领先 `release/*` 超阈值则告警 | 提醒回灌，防再次「带病出厂」 |
| 打包内含真开局冒烟 | `package-deploy.mjs` 内调 `deploy-smoke` | 产物「能起服不能开局」直接打包失败 |
| 解包复验 | release-asset CI：解包到独立 tmp 目录 + 跑 `deploy-smoke` | 上传前拦住 |
| 包内自验收 | 包内 `scripts/verify.mjs` + `./deploy.sh` | 部署方一条命令自证 |
| 单部边界断言 | `verify.mjs` 第 ③④ 步（`/api/levels` 只含本部；他部 404） | 夹带别部内容立刻红 |
| schema 形态自检 | 服务端启动期 `schemaSelfCheck` | 编译链丢 tsconfig 时启动即退 |

## 六、每部开工时的切分清单

做第二部（2.x）时，按此清单执行：

1. `git switch main`，确认所有 1.x 的回灌已回到 main
2. 写 `DEPLOY.light.md`（照 `DEPLOY.md` 改部名/关卡数/首关；打包器缺这份文档会直接拒绝打包）
3. `git switch -c release/2.0-light`，`node scripts/bump-version.mjs 2.0.0`
4. 打包验证：`node scripts/package-deploy.mjs --temple light`（自动剪裁 + 真开局冒烟 + 包内自验收）
5. CI 增加 `release/2.0-light` 的 determinism 单部作业
6. 推 tag `2.0.0`，`release-asset.yml` 按 tag 主线号自动选 `--temple light`

> 第 3–6 步已是机械工作：打包器/验收脚本/部署脚本全部按 `--temple` 参数化，**不再有
> forest 硬编码**（2026-10-28 已落地，见 §七）。
