# r17 · DOM 皮肤与整张游戏图集解耦（2026-10-21）

> 战役第 17 轮。方向从 r16 的"进房段音频"切到**HTML 解析期就开拉的资源**：连接面板（石板大厅）
> 是纯 DOM，它的 CSS 背景用负 `background-position` 从三张**整游戏图集**里取帧，于是 1241.1KB
> 的石板/按钮/头像坐在冷启动最靠前的 60ms 里，与 phaser chunk 抢 HTTP/1.1 的六条连接。
> 本轮不改一像素的设计——只把这 6 帧换到一张 82,107B 的专用合成贴图，并为此补上 DOM 侧
> 唯一存在的逐像素回归面。单位口径同 `perf-load`：下文 KB = 1024B。

## 一、量具（两件，`3a5848b`+`98d383f`+`83d27a3`）

| 量具 | 能力 |
|---|---|
| `scripts/e2e/domskin.mjs`（新门禁） | DOM 皮肤四态逐像素对拍（wide-idle / wide-hover / wide-error / narrow-idle），覆盖面板全部 5 处皮肤引用。判据 **SHA-256 逐字节相等、零容差**；FAIL 打 `magick compare -metric AE` 并把差图落 `TEMP/domskin/`。基线 `benchmark/results/domskin/`，代次记在 `manifest.json` 的 `provenance` |
| `scripts/build-dom-skin.mjs`（生成器） | 对着 `assets/atlasses/*.json` **断言** 6 个帧矩形（素材重打包即红），裁片拼成 1082×988 + 2px 透明隔离带；回读用**原始样本**逐字节全等证明无损；断言隔离带全 0、辅助块集合与图集一致；`--check` 重跑字节可复现 |

为什么 DOM 侧需要单独一个门禁：canvas 的 `visual-diff` 拍不到 DOM，`journey` 只看 `textContent`，
`route` 只看权威 state——"把 CSS 背景改指别处"这种纯字节面动作，只要有一个像素坐标算错，
用户看到的就是错位石板/半截按钮，而三条既有门禁全绿。本轮之前这条面是裸的。

首版两次误判（都写进脚本头，是量具的口径资产）：
1. **CSS 时间基**：`.menu-logo` 的 `menu-floaty 4s` 无限浮动让同版本两次截图差出 1%~3% 像素，
   首版据此判"皮肤变了"。截屏前 `animation/transition:none` 冻结（两侧同规则故可比）后归零。
2. **背景图解码竞态**：`background-image` 不参与 `img.complete`、也不被 `document.fonts.ready`
   覆盖，首版没等它，把"715.2KB 的 CharAssets 尚未解码"读成"头像没画"。改为遍历 `#menu *`
   的 `::before/::after` 计算值收集全部 URL 逐个 `Image.decode()`。修完四态复跑两次逐字节相同。

## 二、归因（基线 `load-r17-base-f01.json`，检出 `e0080b2`，forest_01 档）

Menu 段 4054KB / 21 请求，其中三条 `type:"css"` 行就是 DOM 皮肤的全部代价：

| 资源 | 传输 | 解码 | 起于导航后 | 落定 |
|---|---|---|---|---|
| `/assets/atlasses/CharAssets.png` | 715.2KB | 714.9KB | 24ms | 81ms |
| `/assets/atlasses/PopupAssets.png` | 334.4KB | 334.1KB | 20ms | 78ms |
| `/assets/atlasses/MenuAssets.png` | 191.5KB | 191.2KB | 23ms | 78ms |
| **合计** | **1241.1KB** | — | 全部在 20–24ms 起跳 | 78–81ms |

三条同时在 20–24ms 起跳、占掉 HTTP/1.1 六条连接中的三条近 60ms，正是 `index-*.js`(31.8KB)
等主 chunk 要下载的窗口；同一份快照里 DCL 233ms、`__fw` 就绪 584ms、Menu active 861ms。
另一条旁证：370ms 时 Phaser 自己 `load.image` 同一批 PNG，传输只有 **0.3KB**（`decodedKB` 仍是
714.9）——**浏览器缓存已命中，即这 1241.1KB 从头到尾只是 DOM 皮肤在替游戏付**，
且付在最贵的时刻。所以本轮的可行解不是"压缩 PNG"（PNG 已不可再压），而是**换一张只装 DOM 需要的 6 帧的小图**。

## 三、门禁第一次跑就抓到的东西：L5（独立 commit `043b2a5`）

新建门禁的基线与"现役实现"应当逐字节相同——第一次跑就不是。AE=1248，localized 在两颗头像框，
最大级差 255。根因不在本轮改动，在既有 CSS：

```css
.btn .av    { background: url(/assets/atlasses/CharAssets.png) no-repeat; }   /* 特异性 (0,2,0) */
.av-fire    { background-position: 0 calc(-862 / 130 * 33px); }               /* 特异性 (0,1,0) */
```

`background` 简写会把未声明的 `background-position` **复位成 `0% 0%`**，而简写所在规则的特异性
高于下面两条定位规则，于是复位赢了：两颗头像自始画的是图集左上角 `water_head_falling0000`
的裁片，**火头从未生效过**。计算值 `background-position: 0% 0%` 与逐像素差图互相印证。
修法即简写改长写（`background-image`/`-repeat`/`-size`），不改视觉意图。

- 纪律入台账 `note/audit/2026-10-21-code-audit/04-fix-log.md` §2.2：**简写复位**这类"更特异性
  的简写覆盖更少特异的长写"，只靠读 CSS 看不出来，必须量计算值或逐像素。
- 顺序上先修 L5、再要求合成贴图与"L5 修好后的画面"一致——两件事分两个 commit，任一可独立回滚。

## 四、实施（件A，`7c19e61`）

`assets/dom/dom-skin.png`（1082×988，82,107B = 80.2KB，sha256 `67acd6ff1f28bfc450bb0741…`）：

| 帧 | 来源图集:帧矩形 | 合成图落点 | 尺寸 |
|---|---|---|---|
| panel | PopupAssets (0,205) | (0,0) | 1082×642 |
| avFire | CharAssets (0,862) | (0,644) | 130×162 |
| avWater | CharAssets (1340,468) | (132,644) | 130×162 |
| btnRest | MenuAssets (0,0) | (0,808) | 252×117 |
| btnHover | MenuAssets (256,0) | (254,808) | 252×117 |
| cross | PopupAssets (1122,205) | (0,927) | 61×61 |

行序 panel / 头像 / 按钮 / cross，每段之间 2px 全透明隔离带——缩放采样核在帧边界只取到透明，
与图集里的邻帧内容彻底解耦（图集侧原本是邻居帧直接挨着，各向异性拉伸时会有 bleed 风险）。

CSS 换算规则（五处引用全改，含 hover 分支与窄屏回流分支）：
`background-position: P` 解算为 `P × (容器尺寸 − 渲染图尺寸)`，所以只要把渲染图尺寸写成
`容器 × (整图尺寸 / 帧尺寸)`，帧就 1:1 铺满容器。两种情形分母不同，这是最容易算错的地方：

- 等比缩放（`... auto`，头像与十字）：帧坐标直接乘缩放比，如 `.av-fire` 的 `calc(-644/130*33px)`；
- 各向异性拉伸（面板、按钮）：除数是 `(整图尺寸 − 帧尺寸)`，如面板纵向 `988/642`、
  按钮横 `1082/252` 纵 `988/117`、静止 y 位 `808/871`、hover x 位 `254/830`。

生成器侧三条硬断言（任一不过即不出图）：帧矩形与 atlas JSON 一致；合成图每帧区域与原图集帧
**原始样本逐字节全等**；辅助块集合与图集一致（图集只有 `IHDR/IDAT/IEND`，多一个色彩块
浏览器就换解码路径）。无损校验实测：6 帧共 **3,197,812** 个 RGBA 样本字节，差异字节 **0**。

## 五、皮肤等价性：逐像素 + 原始样本两层

原始样本层已经证明"内容一模一样"，但浏览器画面是否一模一样不是同一回事——源图从
2048×2048/1024×1024 变成 1082×988，Chrome 的重采样相位随之改变。四态实测（旧基线 `043b2a5`
的图集皮截图 vs 现役合成贴图皮，`magick compare`；8-bit 下度量按 0–65535 报，括号内为归一值）：

| 态 | AE（像素数/归一） | 超 1% 容差 AE | MAE | RMSE |
|---|---|---|---|---|
| wide-idle | 21538（0.0175） | 234 | 3.156（4.82e-5） | 55.05（8.40e-4） |
| wide-hover | 21502（0.0175） | 218 | 3.153（4.81e-5） | 55.90（8.53e-4） |
| wide-error | 21720（0.0177） | 294 | 3.233（4.93e-5） | 56.38（8.60e-4） |
| narrow-idle | 35963（0.0937） | 6037 | 79.95（1.22e-3） | 676.7（1.03e-2） |

分区诊断（数值定位，未读图；旧图从 `git show 043b2a5:benchmark/results/domskin/<id>.png` 取回，
差值用逐像素三通道最大差转灰度后取 `fx`）：

| 区域 | 最大级差(0–255) | 区均(0–255) |
|---|---|---|
| wide-idle 整幅 | 39.6 | 0.0149 |
| 石板 1082×642 @(99,223) | 39.6 | 0.026 |
| 左上角裁片 74×74 @(99,223) | 1.7 | 0.611 |
| 创建钮 252×117 @(384,587) | 32.0 | 0.024 |
| 火头像 33×41 @(433,625) | 32.0 | 0.517 |
| 水头像 33×41 @(704,620) | 39.6 | 1.203 |
| wide-hover 整幅 | 39.6 | 0.0149 |
| narrow-idle 整幅 | 74.3 | 0.326 |

读法：**整幅均值 0.015/255、最大 39.6/255**，且大值只出现在石板棱边与头像边缘的少数像素上；
石板中位平坦处逐像素 ≤2（左上角裁片整框级差 ≤1.7）。这是"同一份内容被换了一个重采样相位"
的形状（相位错开半个滤核 → 棱边大值、平坦小值），不是"画错了东西"的形状。
窄屏差到 74.3/0.326，因为面板在各向异性拉伸分支下，两侧拉伸的**源尺寸**不同（2048 vs 1082）。

灵敏度对照（证明这套判据不是"松到看不见"）：同一条 `compare` 口径下，§三 的 L5 错帧是
AE=1248 / 最大级差 255 / 集中在两颗头像——**级差直接顶满量程**，与本轮"源尺寸变了"的分布
完全不同。这也是本报告为何坚持用两个层面各自表态：内容等价用原始样本（0 差异字节），
画面等价用逐像素表（给数不给"看起来一样"）。

据此定判据：**门禁保持零容差字节相等**，本轮属于**有意的画面换代**，按脚本头写好的三步流程
（先量出上面这张表→写进本报告→`--save` 刷基线，代次记进 `manifest.provenance`）收口。
不为一次改动放宽容差——宽容差会让下一轮的"错位半帧"变成绿灯。

## 六、收益与代价（`load-r17-base-f01.json` vs `load-r17-after-f01.json`，同档 forest_01、两轮各取）

先说结论里最不顺眼的一条，把它摆正：**本轮全链字节是负的（+79KB）**，收益在 Menu 段、连接争用与解码位图面。

基线里 PopupAssets.png 的 CSS 行在 20–78ms 把这 334.4KB 拉完，于是 1148ms 时 Phaser 自己的
XHR 只花了 **0.3KB**（缓存命中）——那三张图集的字节本来就是**要下的**，DOM 皮肤只是把
同一笔账提前、并挪到了最贵的窗口。件A 把 DOM 侧换成 80.5KB 小图后，PopupAssets 的 334.4KB
退回点击后真实下载（1208–1239ms，31ms 落地）。逐段账：

| 口径 | 基线 `e0080b2` | 现役 `7c19e61` | 差 |
|---|---|---|---|
| Menu 段传输 | 4054KB | 3799KB | **−255.0KB（−6.3%）** |
| Menu 段请求 | 21 | 19 | **−2** |
| 点击→Game 段传输 | 2697KB | 3031KB | +334KB（= PopupAssets 回落本段） |
| 进 Game 累计（全链） | 6751KB | 6830KB | **+79.0KB** |
| 全链请求 | 54 | 52–53 | −1～−2 |
| DOM 皮肤 CSS 行 | 3 条（1241.1KB，20–24ms 起跳，占 6 连接中 3 条近 60ms） | 1 条（80.5KB，26–74ms） | 争用 3→1 |
| DOM 侧解码位图（w·h·4 名义） | 36.00MiB（2048²+2048²+1024²） | 4.08MiB（1082×988） | **−31.92MiB（−88.7%）** |
| 复验（同站再导航） | 6735.9KB→0KB | 6816.1KB→0KB | 免重传性质不变 |

里程碑（两轮均值，本地口径噪声带 ±120ms，只作方向核对不作收益主张）：

| 里程碑 | 基线 | 现役 | 差 |
|---|---|---|---|
| DCL | 232.5ms | 234.5ms | +2.0 |
| `__fw` 就绪 | 489.5ms | 433.0ms | −56.5 |
| Menu active | 754.5ms | 732.0ms | −22.5（两轮 861→773、648→691，方向相反＝带内抖动） |
| 点击→Game | 1502ms | 1416ms | −86 |
| 暖重载 Menu | 715ms / 5KB | 813.5ms / 4KB | +98.5 / −1KB（带内） |

因此本轮的裁定是**结构收益为正、字节收益为负、里程碑不 regress**：
LAN 双人场景下 +79KB（≈0.06s@100Mbps）不是用户可感代价，而 Menu 段 −255KB、争用 3→1、
DOM 解码位图 −31.92MiB 是确定的。**不补 `fetchpriority=low` 的图集 preload**——那会把提前
下载的老问题换个写法再引进来；里程碑没有需要抢救的回退。

另记一条与本轮无关的观察：`audio.count` 17→18 而曲目并集与 `totalKB`（1988.6）完全相同，
是同一条 BGM 被记了两次请求行，不是多下一首歌。

## 八、下一轮候选（本轮未做，已量到边界）
