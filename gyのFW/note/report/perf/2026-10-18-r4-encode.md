## 一、头号发现（勘误）：基准累积伪影，r0/r1 的 encode 段数字放大 9~29×

**机制**：@colyseus/core `SchemaSerializer.applyPatches` 在发送 patch 后调用
`encoder.discardChanges()` 清空变更集（`node_modules/@colyseus/core/build/serializer/SchemaSerializer.js`）。
r0 起的 perf-serialize/perf-sync 基准**缺这一步**——变更集自房间起点累积，每次 encode 把
「自始变更过的所有字段」按最新值重编码。量出的 patch 不是生产每网格的真增量，enc/dec CPU
与线路 KB/s 同步被放大。实证（TEMP discard-check 件，收容 tools/perfopt4/）：

| 关 | 旧口径 patch（r0/r1 存档） | 生产口径 patch（补 discard） | 倍数 |
|---|---|---|---|
| forest_01（scripted@60Hz） | 370B | **50B** | 7.4× |
| forest_12（scripted@60Hz） | 450B | **58B** | 7.8× |
| forest_bonus_2（scripted@60Hz） | 2685B | **91B** | **29.5×** |
| forest_01（idle） | 347B（perf-sync 20Hz） | **4B**（不含协议占位；含则 5B） | ~70× |

**连锁勘误**（r0 报告 §五/§六结论的再修正）：

1. **encode 段生产真值 0.07~0.21ms/仿真秒**（纯 encode 计时：f01 0.0012 / f12 0.0013 /
   bonus_2 0.0034ms/tick），非 r0 口径的 0.65~3.08——放大 9~13×。tick 链占比
   **f01 ≈4.5%、bonus_2 ≈1.1%**（vs step+sync），非"~10%"；r0 hotspot 的 encode 8.7µs
   同为伪影口径。
2. **60Hz 出站线路真值 2.93/3.39/5.36KB/s/客户端**（scripted 上界），非 21.7/26.4/157.3。
   r0 §六判读 5 归因 netopt 实测 1.95KB/s 与基准 21.7KB/s 的差距为「负载差（上界 vs 典型）」
   ——主体实为本伪影；修正后两口径同量级，r0 该节的"最坏带宽"数字不可再用。
3. **非空率 100% 结论维持**（timerMs 每 tick 变化，开局后每网格必发包），但 idle patch
   真值仅 5B——timerMs 一个字段就是整个 idle 包（§四）。
4. r1 件3 的「patch 347B/2646B 逐字不变」等价性结论**不受影响**（双路径同伪影下逐字节相等
   ⟹ 真增量亦相等；本轮 4 关×600 帧双路径门禁在生产口径下复证）。

## 二、剖析证据（STEP1；工具与数据收容 `note/report/perf/tools/perfopt4/`）

- **CPU profile（inspector Profiler，20µs 采样）**：累积口径 bonus_2 全循环（step+sync+encode）
  schema 模块 self 9.5%——encode 走查 3.10% / number$1（msgpack 动态数编码）1.26% /
  **$filter 1.12%** / encodeSchemaOperation 1.21% / encodeValue 0.40%。生产口径 f01：
  encode 编码侧 self ≈4.6%，而 **setter 变更跟踪侧（set 3.90% + change 1.06%）≈ 编码本身**
  ——轻关下 @colyseus/schema 的写跟踪比编码贵，属 vendor 内部（r1 已优化其外的取数路径），
  本轮不动。
- **快照字段盘点**（逐 tick 全叶字段 diff，600 tick）：
  - f01 idle：唯一变更字段=timerMs（4B 字段层）→ patch 5B。**timerMs 即整个 idle 包**。
  - f01 scripted：players 39.1B/tick（x 10.9/vx 10.9/y 7.5/vy 6.1/anim 2.8/headTilt 0.6/facing 0.3）
    + timerMs 4.0 → patch 50B。
  - bonus_2 scripted：players 39.6 + platforms 14.3（y 11.8）/props 10.4（y 10.3）/pulleys 4.5
    + timerMs 4.0 → patch 91B。钻石/门/风等低频字段稳态零变更。
- **encode 结果复用（STEP2 候选 3）——内置证实，无需动作**：`applyPatches` 无 filter 路径
  encode 一次得 `encodedChanges`，同 buffer 发给全部客户端（`SchemaSerializer.js` L90-98；
  RoomState 无 @filter/@view → hasFilters=false）。每 tick 每房一次编码，与订阅者数无关。

## 三、件2 细节（$filter 遮蔽）

- 位置：`packages/server/src/rooms/state.ts` 末尾对 8 个 schema 类
  （RoomState/PlayerState/DiamondState/LeverState/PusherState/BodyState/WindState/DoorState）
  定义自身静态 `[$filter] = undefined`（own property 遮蔽继承静态）；
  `colyseus.cjs.ts` 仅补 `$filter` 再导出（同 CJS 实例约束，见该文件头注释）。
- **字节等价论证**：全仓库 `$filter` 唯一读取点在 `Encoder.encode`（schema cjs L4235）
  `filter && !filter(ref, fieldIndex, view)`——view=undefined 时 vendor 实现恒返回
  `tag === undefined` = true（本树无标签），遮蔽后短路跳过调用，编码决策不变 → 出站字节
  逐字不变。`hasFilters` 由 metadata view 标签驱动（TypeContext.discoverTypes），不受影响；
  encodeView 路径（StateView）无标签即不可达。
- **门禁实测**：TEMP ab-filter 件（收容 tools/perfopt4/）——同进程双路径（vendor 缺省 =
  delete 遮蔽恢复继承 vs 本件行为），4 关（01/04/12/bonus_2）×600 帧 scripted，逐帧
  patch 字节 + 逐帧 encodeAll 字节全部相等；det 48/48 位级一致；fixtures 6/6 同值。
- **收益带**：交错 A/B（9 轮中位，同进程同 JIT）f01 -10.1%/f12 -12.0%/bonus_2 -3.7%
  （重关 patch 字段多、走查占比大，filter 份额相对小）。绝对 0.0001~0.0002ms/tick
  ≈ 0.006~0.012ms/仿真秒——诚实定位：**协议兼容性零风险的顺手件，非本轮主收益**。

## 四、评估弃件：timerMs 降频出站（候选 2，未实施）

任务书要求谨慎评估的协议行为变更（纯显示字段降频 10Hz + 客户端插值补偿）。数据评估：

- **客户端消费面**：timerMs 全仓唯一读者 = `GameScene.ts:1304` mm:ss HUD（秒粒度；r3 件1
  起整秒不变跳过重算）→ 10Hz 出站视觉零差。e2e journey 的 timerMs 冻结断言不受影响
  （暂停=服务端停钟零发包）。
- **收益上界**：idle 期 timerMs 是唯一变更字段（patch 5B 含协议占位）→ 60Hz 全速发包
  载荷 300B/s/客户端（+WS 帧 2B/包 + TCP/IP ~40B/包 ≈ 线路级 <3KB/s）；active 期省
  4B/tick ≈ 240B/s 载荷（f01 patch 的 8%、bonus_2 的 4.4%）。
- **结论：弃**。带宽绝对量已小（idle 线路 <3KB/s/客户端 vs r0 伪影吓出来的 157KB/s），
  而代价=协议行为变更 + 客户端补偿路径 + visual-diff/e2e/真机带宽全复测 + 协议变更披露
  节——成本收益不成比例（任务书预置的放弃判据「带宽绝对量已小」成立）。r4 勘误后，
  netopt 11 号档「60Hz+客户端平滑」决策的价签进一步降低，维持不动。

## 七、一句话总结

**勘误为主、微优为辅：r0/r1 的 encode 段数字系基准缺 discardChanges 的累积伪影（patch
2685B→91B、encCPU 3.08→0.21ms/仿真秒、60Hz 线路 157→5.36KB/s/客户端，生产占比 ~1-5% 非
~10%）——件1 修基准口径并全量披露；件2 声明侧 $filter 遮蔽轻关 encode 段 -10~12%（字节
逐字不变，det 48/48+fixtures 6/6）；timerMs 降频经数据评估弃（idle 线路 <3KB/s 不值协议
变更）；encode 跨订阅者共享证实为 Colyseus 内置。**
