## 本轮换的角度

此前 48 轮里，「选关树浮雕纹理烘焙」只在 r48 被顺带量到过一次总时长（`perf-temple`
的 1147ms 入场路径），**从未拆过内部**。而它在每局开始、每次换庙、每次点 Play 都要走，
且 `templeTreeBake.ts` 头注自称「≤50ms/帧约束」但实际调用是 `stepTreeBake(key, 8)`。
本轮把这条链从「黑箱 350ms CPU」拆到 stage 级，并做配对 A/B。

## 49.1 先纠正一个错误前提（本轮最重要的方法论产出）

首版量具用的是**合成输入** `sparse`（每 3px 一个点铺满全高，覆盖率 2.1%），据此得出
「行级短路对真实形态只有 +0.6%」。**这是错的**：我从未量过真实 alpha 分布。

用 `benchmark/dump-tree-alpha.mjs`（钩 `getImageData` 抓烘焙读回的整层像素）导出 forest 真实
alpha 后，结论完全相反：

| 层 | 覆盖率 | 有 alpha 的行 | R=7 窗口空占比 |
|---|---:|---:|---:|
| big（底影 t200/outer1） | **39.83%** | 93.1% | 48.9% |
| all（全树 t200/outer0） | **29.57%** | 91.4% | 58.0% |
| done（金星 t180/gold） | **0.58%** | 8.3% | 99.2% |

**真实厚层是稠密的，不是稀疏的。** 我造的合成输入把结论量反了——这直接导致第一版
「行级短路」优化在真实数据下无效（`rowAllZero` 几乎不触发），已撤回。

> 教训：合成输入只能用来探路，**绝不能用来下「对产品是否有效」的结论**。本轮把它写成
> 量具头注与测试注释的一部分（见 49.6）。

### 顺带发现：`toBaked` 的 1.5–2.0s 里大部分不是 CPU

`perf-bake.mjs`（浏览器口径）+ CDP CPU profile 显示 `(program)` 占 **70.3%**

## 49.3 主线一：`outlinePass` 的三角函数写在逐像素内层

```js
for (const ang of angles) {
  const v = sampleA2(..., t0x - offX * Math.cos(ang), t0y - offY * Math.sin(ang));
}
```

`angles` 是循环不变量（20 个），但 `Math.cos(ang)`/`Math.sin(ang)` 在**每个像素**重算。
真树数据下进入该循环的像素数是 202,271（实测），即 **810 万次三角函数调用**。

`perf-bake-cpu.mjs` 的分支计数（all 层真实 alpha）：

```
canvas 1036x864 = 895104 px
  ownA>=0.1 直接返回 : 143371 (16.0%)
  窗口空 跳过        : 549462 (61.4%)
  进入 20 角循环     : 202271 (22.6%)  → 4.05M sampleA2
```

改成预计算 `(cos,sin)` 对表后内层只做乘法。

**配对 A/B**（真实 alpha，9 轮交替，每轮校验位级一致）：

| stage | A 参照 | B 当前 | Δ | 判定 |
|---|---:|---:|---:|---|
| outline / all 20 角 | 134.5–140.3 ms | 53.7–77.7 ms | **−61.8% ~ −42.2%** | **区间分离** |

（两次独立运行分别 −61.8% 与 −42.2%，方向与量级一致。差异来自 B 臂区间上界抖动，
两次都区间分离。）

## 49.4 主线二：`bevelColorMatrix` 的偏移量逐像素重算

```js
for (const o of offs) {
  const ox = o * WTX, oy = o * WTY;   // 与像素无关，但每个像素都算
```

hoist 成 `offXY` 常量表。纯常量提取，位级必然相同。

**配对 A/B**（真实 alpha，9 轮交替）：

| layer | A 参照 | B 当前 | Δ |
|---|---:|---:|---:|
| big t200 outer1 | 60.1 | 53.9 | −10.3% |
| all t200 outer0 | 53.9 | 46.0 | −14.6% |
| done t180 gold | 7.3 | 7.0 | −4.2% |
| 三层合计 | 120.9 | 106.9 | **−11.6%** |

**判定：带内，不主张。** 三层方向一致但都小于 ±10% 噪声底（done 层某次 −9.4% 分离，
换次运行又带内）。按 r47/r48 纪律，只有方向一致 + 零风险 + 零复杂度才留——这条满足
（纯常量提取），故保留但**不宣称减速**。

## 49.5 被撤回的方向：`sampleA2` 采样坐标表驱动

`sampleA2` 每次做 2 次 `Math.floor` + 8 次边界比较，而 `(xa,xb,fx)` 只依赖
`(像素列, 采样项)`。看起来是最肥的目标。

**微基准（`TEMP/r49-tables.mjs`）显示 −51.7%**，于是实现了完整表驱动版本并提交。

**真实全链配对 A/B 推翻它**：

| layer | A（逐像素） | B（表驱动） | Δ | 判定 |
|---|---:|---:|---:|---|
| big | 59.5 | 57.6 | −3.3% | 带内 |
| all | 53.8 | 47.9 | −11.1% | 带内 |
| done | 7.4 | 7.2 | −2.5% | 带内 |
| 合计 | 120.7 | 112.7 | **−6.6%** | 带内 |

**为什么微基准骗人**：它只测采样循环本身，不含建表（`nEntry × (w+h)` 项）与每像素
多一次表索引的缓存压力。而 bevel 有 61.4% 的像素被 `satSum` 空盒判定提前跳过、
根本不进采样循环——微基准正好测了最有利的那 22.6%。

**已 revert。** 理由：收益带内 + 复杂度显著上升（+60 行、~8300 项内存）+ 曾踩 1 ULP 坑
（见 49.6）。代码里留了注释记录这次失败，避免下次再走一遍。

## 49.6 本轮抓到的实际缺陷：合成单测给不了的等价性保证

表驱动的实现里漏了一个 `fr()`：

```js
a = sampleE(0, x, yi);          // 错：漏掉 fp32 化
a = fr(sampleE(0, x, yi));      // 对
```

**33 条合成单测全绿**，真实数据必红（首个差异在字节偏移 613864）。

事后量化这个盲区：

| 探测 | 结果 |
|---|---|
| 24×20 随机噪声，144000 像素，漏 `fr` | **显形 0 次** |
| 均匀块，255 种 alpha 值全试 | **显形 0 次** |
| 真实全画布 1036×864 结构化数据 | **显形（必红）** |

原因：`fr()` 直接作用于 alpha 通道时 0/256 个值受影响（`round(a*255)` 吸收舍入），
差异只在 `gray*a` 的 double 乘法跨过 Uint8 台阶时显形——需要真实的连续密度分布。

**结论（写进 `perf-bevel.mjs` 头注与测试注释）**：
> 合成输入不能替代真实数据做等价性判定。单测保证「常规路径等价」，
> 真实数据等价性必须靠配对 A/B 量具（每轮位级校验 + 失败退出 1）。

另修了两个浮点细节，都是位级等价的必要条件：
- 坐标分解必须逐字同序：`t0x=(x+0.5)*FX → tx=t0x+ox → px=tx−0.5`。
  合并写成 `(x+0.5)*FX+ox−0.5` 会在边缘像素产生 1 ULP 偏差。
- `FX = canvasW/Cf = 1036/1036.8 = 0.99923`（**不是 1**），`FY = 1`。
  这个「极接近 1 但不等」的区间是最容易出事的地方。

## 49.7 页面口径：内核 −27.8% 兑现多少

**CPU 内核合计：255.8 → 184.6 ms（−27.8%）**，位级全一致。

页面口径（`perf-bake.mjs` 的 `toBaked`）需要严格区分三种数字：

| 来源 | 结果 | 判定 |
|---|---|---|
| 跨会话对比（基线 03:13 录，当前重跑） | 3968.6 → 1599.7 ms（−59.7%） | **不可采信** |
| **同会话交替 A/B**（`TEMP/r49-page-ab.mjs`，装 dist 交替，各 10 轮） | **2254.0 → 2251.7 ms（−0.1%）** | **带内，不主张** |

**跨会话那个 −59.7% 是假象**：基线 `bake-r49-b8.json` 的 `bakeSegment 2868ms` 与当前
`922ms` 的差距，主要来自**当次运行环境的帧率差异**——r49 早期已实测：budget=8ms 时
headless 帧率本身只有 ~13fps，`bakeSegment` 被帧数而非 CPU 主导。这条只作为
「headless 口径不可跨会话比较」的反例记录。

**同会话 A/B 才是真结论：−0.1%，完全带内。** 两条臂的区间几乎完全重叠
（A 1849.8–2719.5 / B 1865.1–2687.5）。

### 为什么内核 −27.8% 在页面里不显形

三层账：

1. **内核只占总时长的 12.5%**：CPU 内核 184.6ms ÷ `toBaked` 2252ms。
2. **内核省下的 71ms 只占 3.2%**，早已被页面路径的 ±20% 噪声（区间跨度 870ms）淹死。
3. **剩下 87.5% 是 headless 环境的合成等待**（`(program)` 70.3%）+ 分帧调度。
   分帧把 184.6ms 的 CPU 摊到 N 帧上，而每帧本身要等 SwiftShader 合成——**帧率是瓶颈，
   不是每帧干了多少活**。

**这是 r49 最重要的诚实结论**：烘焙内核的 −27.8% 是**真实但不可感知**的收益。
它在真机（有 GPU 合成、帧率高）上才会转化为入场延迟下降；在 headless 口径里
无论内核多快，`toBaked` 都由帧数 × 每帧等待决定。

> 若要在 headless 里兑现内核收益，唯一办法是提高 `stepTreeBake` 的每帧预算
> （实测 8→48ms 时 `bakeSegment` −53.3%、8→200ms −81.0%），但那会让单帧 p95
> 飙到 240–280ms（r49 早期实测），**玩家可感知卡顿，不可接受**。且这条与内核优化
> 是两回事：预算是「把工作挪到更少的帧」，内核是「把工作变少」。

## 49.10 结论与遗留

**可主张**：
- `outlinePass` 三角函数外提：**−61.8% ~ −42.2%，区间分离**（两次独立运行均分离）
- 烘焙 CPU 内核合计 **−27.8%**（绝对耗时，位级一致）

**不主张**：
- `bevelColorMatrix` 偏移量外提 −11.6%（带内，但零风险故保留）
- **页面口径 −0.1%，完全带内**（同会话交替 A/B，各 10 轮）——内核收益在 headless 里
  不可感知，见 49.7 的三层账

**撤回**：
- 行级短路（真实厚层 93% 的行有 alpha，前提错误）
- `sampleA2` 表驱动（微基准 −51.7% → 真实全链 −6.6% 带内）

**遗留**：
- `premultToStraight` 占 5.2%（14.7ms），逐像素除法，未动（收益不足以立项）
- `alphaSat` 占 4.7%（13.3ms），与 `buildSAT` 重复遍历一遍，理论上可合并但两者
  在 `stepTreeBake` 里分属不同任务（分帧需要），合并会改变单帧预算曲线
- **`bevelColorMatrix` 仍是最大头（106.9ms / 58%）**，但本轮已证明：
  任何依赖 `sampleA2` 加速的方向都被「61.4% 像素不进采样循环」这个事实压死。
  下一步若要继续，方向应是**减少进入采样的像素数**（提高 `satSum` 判定精度），
  而不是把采样写快。
