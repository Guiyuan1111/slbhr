# r6 容量基准（perfopt6b 槽）：单进程服务器能带多少房间/客户端

日期：2026-10-18 ｜ git：ab68e0e ｜ 量具：`benchmark/perf-capacity.mjs` ｜ 快照：`benchmark/results/capacity-r6b.json` + `capacity-r6b-ext.json`（+ 前任遗留 `load-r6-before.json` 冷启快照一并入库）
环境：VMware 客机 8 vCPU / Node v22.22.1 / Linux；服务器只绑 127.0.0.1（量具自管生命周期，红线遵守）

## 1. 口径

- **模拟客户端**：colyseus.js 轻量脚本客户端（Node 拉起，不拉真浏览器——容量是服务器侧口径）。上行与生产对齐：66ms 强制重发（`input.ts` RESEND_MS 同款 ≈15Hz/端）；移动图案 walk（左右换向持续走动，本跑全程 0 死亡）。ws 层按首字节分类字节计数（15=state patch / 13,17=广播消息）。
- **房间**：ForestRoom 真房（create+joinById 成对入房，双人到齐 → ready 2.0s → started），阶梯**累计**爬载（前档房间在后档窗内继续跑），60Hz 出站 patch（生产缺省）。
- **每档测量窗 12s**：服务器进程 CPU%（/proc utime+stime，top 独立交叉核验过）、RSS（3 采中位）、每客户端下行/上行 KB/s、patch 到达率、`timerMs` 时漂、死亡/重开数；负载发生器自身 CPU 记录入档（≥95% 记 measure-invalid，本跑最大 36% 未触发）。
- **降级判据**（任一触发=该档降级）：cpuSat CPU≥95%；driftBad 时漂≥2%；patchLow patch 到达率中位<54/s（60Hz 的 90%）。首个降级档=容量拐点。

## 3. 结论

- **拐点 = 96 房（192 客户端）**：patch 到达率跌破 54/s，客户端可见更新粒度从 16.7ms 变粗到 ~21ms（128 房 ~28ms）。
- **降级形态不是物理超步**：`timerMs` 时漂全程 ≤0.34%（判据 2% 未触发）——累加器驱动的固定步长模拟在 CPU 84.8% 时仍咬住实时；先退化的是 patch 网格节奏（事件循环延迟使 patch interval 晚点、每包携带更多累积增量），不是模拟本身。步进超 16.6ms 的红线在本阶梯内未破。
- **CPU 模型**（主跑六点最小二乘）：CPU% = 12.55 + 0.644×房数 → 单核算术上限 ≈**135 房 / 270 客户端**；判据拐点（96 房）先于 CPU 饱和（~157 房外推）出现。每房边际 0.644% 核 = 6.4ms/s，是 r4 微基准物理口径（forest_01 step 1.04ms/sim-sec ≈ 0.10% 核）的 ~6 倍——差额为 syncState+encode+ws 系统调用+定时器+GC 的进程级真实开销（r4 三项可解释 ~1.8ms/s，余 ~4.6ms/s 记进程常杂，未再深拆）。
- **单房间内存增量**：主跑拟合 RSS = 126.3MB + **1694KB/房**（截距与实测空载 131MB 吻合）；2GB 预算外推 ≈1163 房——内存远不是瓶颈（延长跑三点拟合 2498KB/房 为小样本伪影，弃用）。
- **带宽**：实测 1.43KB/s/客户端（forest_01 walk：机制基线 ~12B/patch + 玩家运动增量 ~13B）。**口径勘伪**：r4 的 5.36KB/s/客户端线出自 `serialize-r4-encode.json` 的 **forest_bonus_2**@60Hz（91B/patch，12 pushers+47 platforms 机关重卡）；forest_01@60Hz 应为 2.93KB/s（50B）。96 房服务器出口按实测 ≈275KB/s、按 bonus_2 最坏口径上限 ≈1MB/s——**公网带宽不构成约束**。

## 4. 对公网部署的建议输入

1. 单 Node 进程（8 核 VM）实测可用容量 ≈**96 房/192 客户端**（首个可感降级档）；留裕度建议 **≤64 房/实例**（拐点 75%）。
2. 瓶颈是**单进程事件循环**（拐点先于 CPU 饱和、且模拟本身还有余量）——横向扩容（多进程/多实例按房间分片）是唯一规模化路径，纵向加核无益于单进程。
3. 带宽与内存都不是约束（≤1MB/s 出口、~1.7MB/房）；选型主要看单核频率与定时器精度。
4. 96 房以下 patch 率 ≥57/s、时漂 ≤0.15%、零死亡零重开——稳态服务质量无衰减。

## 5. 复现

```
node benchmark/perf-capacity.mjs --rooms "4,8,16,32" --secs 12 --save <label>          # 缺省 hop 图案（原地跳，零死亡）
node benchmark/perf-capacity.mjs --rooms "64,96,128" --pattern walk --save <label>-ext # 延长阶梯追拐点
node benchmark/perf-capacity.mjs --compare <label>
```
服务器崩溃时量具自动留档（TEMP/perfopt6b/capacity-crash-*.json + results 同名 JSON 带 crashed 标记）后以 exit 2 退出，不掩盖。

## 6. 存疑与披露

- **排程披露**：按派发应在开工 15-35 分钟窗放全曲线；实际因量具编写+三处量具缺陷修复（窗口尾读数错位致速率虚高 ~12% 的时漂伪影、正常收尾误报 crash、空载 RSS 单点采样）+CPU 归因诊断（cpu-prof SIGPROF 自代价 7.5% stime 的干扰识别、按线程拆账）超窗 ~6 分钟，放曲线前已确认机器空闲、无他槽负载在跑。
- walk 图案是"持续走动"的近似，不等于真人操作分布（真人有跳跃/停顿/机关交互）；机关重关卡（forest_bonus_2 类）每房 CPU 会显著高于 forest_01（r4：step 0.29ms/步 vs 0.016ms/步 ≈ 18 倍），容量数字按关卡负载分布打折使用。
- 负载发生器与服务器同机（容量口径即"同机单进程能带多少"）；发生器自耗 CPU 已逐档记录（7.1%→36%），距 95% 失效线远。
- utime/stime 未在本报告拆分定量（诊断期受 profiler 自代价污染，正式跑未拆）；stime 占比与 loopback TCP 路径的关系挂账未查。
- 前任两个原型（proto-room 直构 Room 链 / proto-server 双端入房）思路被吸收，原型文件随本槽收尾清理。
