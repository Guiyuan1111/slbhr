- Arr：−0.14µs/帧（**重叠，进程内即不主张**）→ 整帧 ≈ −1.4µs
- NoMap：−0.47µs/帧（分离，进程内可主张）→ 整帧 ≈ **−4.7µs**

**天花板 −4.7µs ≪ 15µs 裁决线**：即使把 Map 查找 100% 消灭并按最激进的
放大系数折算，也只占整帧 <3%，且低于整帧消融的噪声底 ±5–7µs——
**判负：重写不做。**

## 54.4 为什么 Map 不是成本（读码 + 测量互证）

平滑器每次调用的真实工作：Map.get → 8 次属性读 + 3 次比较分支 → 少量浮点
乘加 → out 对象写。进程内 3.69µs/100 次 = **37ns/次**，其中 Map.get（V8
inline cache 命中的 string-key 查找）只占 ~5ns——**大头是属性访问与浮点**，
而这两样在页内被渲染栈挤出缓存后放大 10×（r51 的「热循环 ≠ 真实帧」）。
数据布局改写能优化的只有那 ~5ns × 10× = ~50ns/次 = **~5µs/帧**，
预估与 NoMap 天花板 −4.7µs 吻合——测量与结构分析对上了。

**推论**：平滑器在整帧口径的 32.9µs 里，可被「连续存储」类改动触及的部分
≤5µs，其余 ~28µs 属于「属性访问 × 缓存驱逐」的物理成本，JS 层面无解
（除非把样本塞进 Float64Array 并自己展开算式——那是把整条平滑管线重写成
数值内核，位级等价风险与工程量都不成比例，且天花板臂已证明收益上限仍
在噪声底边缘）。**r51 挂账就此关闭：`updateMechs` 在 JS 层已无下手点。**
