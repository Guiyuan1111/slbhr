## 根因：c55b352 的公式推导存在三处系统性错误
c55b352「五弹窗面板布局对齐 oracle」从 bundle 源码推导 layoutContent 公式，但：

1. **锚点换算多算一重**：推导时把「钮组 anchor=0」当真并额外加 +126/+58.5 中心换算。
   实测 oracle 结构是**组内子精灵 anchor(0.5) 挂组原点——组位即按钮中心**，
   layoutContent 返回的 (±halfW/3, 0.15·halfH)/(0, 0.5·halfH) 本身就是钮中心，无需任何换算。
2. **textHeight 误用 70**：70 是文本对象高（68.25 四舍五入）的误读；真值 = lineHeight 52 × 0.75 = **39**
   （标题 y = 板顶 + 39）。
3. **GameOver x 系数误置**：把 y 系数 0.4 误抄到 x 上，双钮 x 被写成 CX±173.2（正确为 CX±halfW/3）。

## 勘误方法（三证法）
- **oracle 实拍**：Playwright + 虚拟钟（`__vt.step(1)` 泵帧）进 forest_01 按 P 停在暂停面板，
  全量遍历 Phaser 2 显示树，沿 parent 链累加世界坐标（无 numpy，纯 PIL）。
- **源码公式**：bundle 反解 layoutContent / IngameMenu 系面板装配代码（组位=钮中心公理）。
- **像素交叉**：标题/角帽/齿轮金色簇检测，与显示树读数互证。

## 方法论教训
- 对账脚本曾全 ✗，系**脚本自身坐标系混用**：getBounds 中心减板背景中心得到的是
  「板内中心原点」坐标，而目标表是「板内左上原点」；且文本节点是标签（钮中心 + (0,−14.08)）非钮本体。
  同口径换算后全部命中——报偏差先查测量工具，再查被测物。
- 「对象高」≠「textHeight」：位图文本的 topOffset 用 lineHeight×0.75，勿拿 getBounds 高度凑数。
