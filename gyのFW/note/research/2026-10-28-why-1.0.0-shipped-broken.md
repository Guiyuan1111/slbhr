# 为什么会出现 1.0.0「能起服、不能开局」——需求侧复盘

> 2026-10-28 ｜ 对应 #51 ｜ 技术根因见 [issues-2026-10-20/51-deploy-startup-crash.md](../issues-2026-10-20/51-deploy-startup-crash.md)
> 本文只回答一个问题：**当时给 AI 的要求是不是不清楚？**

## 一、结论先说

要求本身没有说错，但**有三处关键约束是「默认对方知道」的**，而对 AI 来说它们是
**不可推断的隐含前提**。这三处任何一处被写成显式约束，1.0.0 都不会以那个形态出厂。

所以更准确的说法不是「要求不清楚」，而是：**要求只写了产出物形态，没写验收语义；
只写了当前动作，没写长期约束。**

## 二、逐条拆：哪些说了、哪些没说

### 2.1 说了的（这部分 AI 执行得没问题）

| 要求 | 落实 |
|---|---|
| 「做一个能部署的包」 | 包确实能解包、能起服、六步验收全绿 |
| 「只发第一部」 | 剪裁确实生效，`/api/levels` 只回 forest |
| 「写部署文档给接手的人」 | DEPLOY.md 有前置条件、逐步命令、故障表 |
| 「服务端权威联机」 | Colyseus 状态同步、双人进房都能跑 |

这些都做到了，而且是可验证地做到了。问题不在这些。

### 2.2 没写、但被当成默认的三处

#### ① 「能部署」被理解成「服务能起来」，而不是「两人能玩完一关」

要求里没有一句定义「部署成功」的判据。AI 只能自己选一个可验证的终点，它选的是
**进程起来 + 端口能连 + 能建房**——这在工程上是合理的最小闭环，但恰好绕过了整个
增量编码路径。

后果：六步验收里第 ⑥ 步是 `create → leave`。房间从创建到离开都停在 `lobby`，
**一次状态增量都没广播过**。`encodeValue` 的崩溃点永远不被触达。

> 如果当时写的是「验收必须包含两人建房并在关卡里实际跑动 8 秒」，这个坑当场就暴露。

#### ② 「不准用 tsx 跑源码」这类约束当时还不存在，因为还没踩到

1.0.0 是第一次做发行包。此前所有运行都是开发机 `tsx watch`，仓库里有 tsconfig，
`useDefineForClassFields: false` 一直被 tsconfig 兜着。**「tsx 的 ESM loader 不读
tsconfig」这个事实，在整个项目历史上没有机会暴露。**

打包时选择「发 TS 源码 + 目标机 tsx 启动」，在当时看是最省事的做法（不用构建步骤）。
它踩的是一个**从未被观测到的第三方行为**，不是需求描述含混。

> 这类问题的正确防线不是「把要求写得更细」——写不出来，因为踩之前没人知道坑在哪。
> 正确的防线是**让失败尽早、尽响**：预转译 + 启动期自检 + 真开局冒烟（现已全部落地）。

#### ③ 「分发线要跟着主线走」没人说过

`release/1.0-forest` 从 0.3.55 切出后就没再合 main。同期 main 落了 26 个提交，
其中 0.3.56（CSP 禁 eval 后 seedrandom 仍用 `new Function`）是**浏览器进 Game 必炸**
的 P0。

这不是 AI 疏忽，而是**当时根本没有「分发线需要定期回灌」这个概念**——项目第一次
有分发线，流程是从零建立的。分支切出去那天，没人知道它会活三个月。

> 现在这条变成了机器检查：`drift-check.yml` 每周比对各 `release/*` 与 main 的差距，
> 超过 20 提交或 7 天闲置就标 DRIFT。

## 三、三个失败为什么叠成「永久卡 loading」

三个独立缺陷各自都不致命，叠起来才是玩家看到的现象：

1. **服务端崩**：tsx 丢 `useDefineForClassFields` → 字段覆盖 schema 访问器 →
   首次增量编码 `encodeValue` 抛异常 → 单房间异常带崩整进程。
2. **客户端也进不去**：CSP 禁 eval 后 seedrandom 仍走 `new Function` → 浏览器
   建房时场景卡在 CREATING。
3. **验收没拦住**：第 ⑥ 步只 create→leave，不触发增量，服务端崩溃完全隐形；
   浏览器用例当时也不在验收清单里，客户端崩溃同样隐形。

于是：**服务端 10 秒后崩、客户端从一开始就进不去、验收报告全绿。** 三个绿
（六步验收绿、包完整性绿、能建房绿）掩盖了三个红。

## 四、这次改的是流程，不只是代码

| 层面 | 加的东西 | 拦住的是哪一类 |
|---|---|---|
| 语言层 | `state.ts` 64 字段改 `declare` | 「转译器可能产出运行时字段」这一类，与 tsconfig 是否随包无关 |
| 启动层 | `schemaSelfCheck` 监听端口前逐字段验访问器 | 任何形式的产物损坏，启动第一秒就退，不等到玩家建房 |
| 构建层 | 服务端预转译 `.js`，包里不再有 TS/tsx | 「目标机环境与开发机不同」这一类 |
| 验收层 | 第 ⑥ 步改「双人 started + patch 持续增长」 | 「能起服不能开局」这一类 |
| 门禁层 | deploy-smoke 在打包后 / CI 解包后 / 源码树三处跑 | 「CI 绿但产物坏」这一类 |
| 流程层 | `drift-check` 周检 + 回灌检查表 | 「分发线安静地腐烂」这一类 |

## 五、以后给这类任务提要求，值得显式写下来的三句

不是要求 AI 更小心，而是把不可推断的前提写成句子：

1. **验收判据要写「用户能做什么」，不写「服务有什么」。**
   「两人建房后能进关卡并跑动 8 秒不崩」比「能建房」强一个数量级。
2. **发行包必须声明「目标机不需要什么」**（不需要 npm / tsx / 编译器）。一旦目标机
   环境与开发机不同，任何「开发机上隐含存在的东西」都是隐患。
3. **长生命周期分支要有到期检查。** 切分支时顺手定：多久必须回灌一次、谁来查。

第 1 条如果当初写了，1.0.0 会在打包当天被发现。第 2、3 条属于「还不知道坑在哪」的
情况——那种情况靠护栏（自检、冒烟、漂移检查）兜，不靠把要求写得更长。
