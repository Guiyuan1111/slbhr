# 自动探索通关方法可行性调研（01 号档）

> 2026-10-15 · auto 调研槽 · 起因：用户问「我们是否能够像引入 npc 一样，使用算法，让机器探索出通关方法？」
> 性质：可行性调研 + 关键数字实测 + 方案推荐。**不含实现**。实测脚本收容同目录 `tools/`。

## 0. 结论摘要（可决策版）

**可行，且本项目是自动搜索的理想宿主；推荐走"混合路线"，不建议上强化学习。**

1. **内核确定性 + 已测速度 = 搜索预算极其充裕**：同输入位级复现（本档 §2.7 实测 IDENTICAL，与 det 48 关基线一致）；活跃整关回放 63µs/帧，ScanPool(7) 稳态 **31 次整关回放/秒**——1 小时 7 核 ≈ 11 万次整关回放。人工初排一天的活，机器扫描是分钟级。
2. **考古结论：bot 系工具不是搜索算法，是"闭环原语步骤机"，且可直接复活升级为搜索框架**（§1）。它死于配额墙，不死于技术失败；其原语库 + `toRouteDoc` 恰好是搜索空间与产线格式之间的现成桥。
3. **推荐路线：原语级闭环搜索（机器粗搜）→ 现有硬化产线（optimize/scan/MC/门禁精修）**。搜索空间的"动作原语"化是关键设计——分支因子从每帧 64 压到每段 ~16，且产出原生兼容 routes JSON。
4. **最大的坑不是搜索，是"内核 WIN ≠ 真机 PASS"**：真机 CDP 0-5ms/事件抖动 + 1/315 的 40ms 离群（mc.mjs:4-7 实测口径），所以搜索目标函数必须含鲁棒性项（±Nf 扰动仍 WIN / MC 失败数），不能裸 WIN 就收。
5. **MVP ≤2 人日**：botcore 原语库复活入库 + 检查点评分函数 + beam 主循环接 ScanPool，产出直入现有产线（§5 路线图）。
6. **理想试点 = forest_15 尾段 7523 跳台像素带**（§6）：现成 94.0% 前缀、失败封闭在 ~32px 落点带、人工开环手段已穷尽（30 平移候选全 141 不动），机器的联合非线性参数扫描正好补这个维度，算力代价 ~分钟级。

## 1. 考古：r05d bot 系工具是什么、走到哪、为何停、能否复用

### 1.1 botcore 架构（note/evidence/forest_05/tools/breakpoint-r05d/botcore.mjs）

**双角色闭环比步骤机**，逐帧驱动内核世界：

- 每角色一条程序 = 步骤列表；每步骤 = `{run(ctx)->input, done(ctx)->bool, name}`（botcore.mjs:9-106）。
- `drive(world, {fb:[...], wg:[...]}, totalFrames)` 逐帧循环：先跑 `run` 取当帧输入、`done` 判过帧推进，再 `w.step(1/60, …)`，全程记录按键沿事件（botcore.mjs:109-154）。
- **`toRouteDoc()` 把事件表直出为产线 routes JSON 同构格式**（botcore.mjs:157-167）——bot 跑通即产线可用的路线文件，零转换成本。
- 死亡/胜利即时短路返回（botcore.mjs:150-151），谓词可读 `mechSnapshot()`（机关 state）——bot3-f05.mjs:14-21 实证杠杆/平台状态可直接当谓词。
- 原语库 S：settle/wait/sleep/hold/**goTo（带预刹车的定点走位）**/jump/jumpDrift/jumpOnto/runJump/stand；S2（bot3/4 内联扩展）：**brakedHop（刹车跳）/edgeDrop（缘口坠落）**。全部闭环（谓词基于体心坐标/速度/接地/机关状态），比开环帧序列抗扰。
- 同款第二实例：note/evidence/forest_02/tools/botcore.mjs + bot-f02.mjs（r02b 的 8 相剧本，forest_02 结构重设计用，含电梯/桥/摆板谓词）。

**定性：这是"人写策略骨架、闭环原语执行"的半自动框架，不是搜索算法。** 它解决的是"手写帧级事件表太苦"，把编排单位从按键沿提升为原语。

### 1.2 走到哪、为何停

- r05b 建 bot 脚手架 → r05c bot3 v3 编码 f05 全路线，卡死在"512台确认"——02号档 §2 弹道证明该跳**结构性不可行**（P1西→西512台全域封死），是路线设计错，不是 bot 机制错（note/evidence/forest_05/02号档 §2）。
- r05d bot4 v4 按弹道预演改编码"东梯零杠杆路线"（bot4-f05.mjs:1-13），工件完整收容于 breakpoint-r05d/。
- **死因 = 配额墙，非算法**：archive-2026-10.md:7（10-14 [token_failed] 五流阵亡，r05d 4h 零终报）、archive-2026-10.md:29（10-13 [1308] 8 槽同殒，r05b 零提交但 TEMP bot 工件齐）、handoff.md:11（10-15 第二轮 token_failed 全灭收容）。bot 路线本身是否内核 WIN 无终局记录（t5v4.json 在已清理的 TEMP/r05d 中，未入库）。
- 此后自动化尝试未再推进（handoff 全文 grep 无后续 bot 迭代）；产线转向人工初排 + optimize 硬化 SOP（note/plans/route-synthesis.md，2026-10-11 定稿）。

### 1.3 复用判断

**可复用，且是 MVP 的正确地基**：①原语库（S/S2 + goTo/brakedHop 等实战校准件）直接成为搜索词汇表；②`drive`/`toRouteDoc` 是搜索内循环与产线出口的现成实现；③bot-f02 的谓词风格证明复杂机关（电梯/桥/摆板）也能参数化。缺的只是三块：搜索主循环、目标函数、并行化——后两者本项目已有近亲（ScanPool、optimize 的 fatal 计数）。

### 2.2 关键推论（搜索预算换算）

- 活跃口径 ~16k 物理 帧/s/核；**ScanPool(7) ≈ 31 次整关（2365f）回放/s ≈ 11 万次/小时**；1500f 口径 ≈ 50+ 次/s。
- 长关（forest_15 全程 7935f）≈ 0.5s/次回放，池(7) ≈ 14 次/s。
- 对比：optimize ±2f 全量 444 回跑，池化后 ~14s（optimize.mjs 注释"串行 ~130s 压到 ~130s/K"，与本档实测 31/s 同量级互证）。
- **搜索根本不会先撞算力墙，会先撞"目标函数设计"墙**（§4.1）。

### 2.3 内核能力盘点（决定搜索形态的四个事实）

1. **任意帧输入注入：支持**。`step(dt, inputs)` 每帧直接吃 `{fireboy,watergirl}` 输入状态（world.ts:238-249），无输入队列/无缓冲——逐帧分支搜索、原语展开、录制回放三种形态都原生可行。
2. **状态可观测面：够宽**。`step()` 返回 WorldEvent[]：death/diamond(kind)/door-open/mech/win 全事件流（world.ts:23-29）；`snapshotPlayer` 给 x/y/vx/vy/anim/atDoor/doorFrame（world.ts:211-233）；`mechSnapshot` 给 levers/pushers/platforms/props/winds/hangings/pulleys/romans 全量 state（world.ts:165-208）；`doors`/`diamonds`/`players`（含 feetContacts 判接地）getter 齐（world.ts:144-162）。**检查点谓词与 reward 所需信息全部现成，无需改内核。**
3. **无状态克隆/快照**：`reset()`= 全量重建（world.ts:429-448），没有 serialize/restore。→ 搜索树回溯只能 (a) 每候选从源头重放（确定性使重放绝对正确），或 (b) **live-worlds**：每 beam 候选持有独立 World 实例只进不退（实测 2.3：并行零惩罚、内存可负担）。
4. **风时基确定性**：缺省 windClock=simTimeS（world.ts:69、105），headless 搜索无需处理风相位随机。

## 3. 方案空间分析（结合实测数字）

> 共同前提：搜索空间按"**动作原语**"组织而非单帧——单帧联合分支 2^3×2^3=64、深度 1500-8000，直接搜必死；原语化后分支 ~16、深度 10-40 段。原语词汇直接用 botcore S/S2 实战库（§1.3）。

### A. 原语序列直接搜索（beam / GA over {原语,参数} 序列）

- **形态**：基因 = 双角色各一条原语序列（GA 天然解耦双角色耦合）；适应度 = 内核回放的检查点评分。beam 变体即"逐段扩展保留 top-K"。
- **可解面**：走/跳/乘平台/杠杆时序类主体关；对多阶段机关耦合关需要检查点引导（否则评分局部极值=卡墙绕圈，微型搜索已观察到 hop 优于 hold 的投机行为——microsearch 输出，目标塑形是主要工作量）。
- **算力**（实测换算）：beam 100 × 分支 16 = 1600 evals/代；420f 段 ≈ 25ms/eval → 单核 40s/代，池(7) ~6s/代；20-40 代收敛 → **小时级 CPU/关（单核口径），池化十分钟级**。
- **成本**：MVP **1.5-2 人日**（botcore 入库 0.5 + 评分函数/检查点格式 0.5 + beam 主循环接 ScanPool 0.5-1）。
- **衔接点（本方案最大优势）**：`toRouteDoc` 产物 = routes JSON → optimize ±1f 硬化 → scan → MC → route.mjs 全链现成。

### B. 分段子目标分解 + 段内搜索

- **形态**：检查点 = x/y 里程碑 + 机关 state 门控 + 存活（§2.3-2 的事件流让"机关已翻转""钻石已收"可直接当断言）；段内 beam/GA，段间拼接。指数压制 = 状态空间分段线性化，是对 A 的必要补充而非替代。
- **拼接的实现约束**：无状态克隆（§2.3-3）→ 每候选评估需"前缀重放"（确定性保证正确性）：forest_15 口径前缀 0.5s/次；缓解 = live-worlds（每候选一个 World，fork 时各自重放前缀一次，之后每代只步进段内 400f ≈ 25ms/候选——50 候选 × 10 代 ≈ 前缀 25s + 段内 12s，**分钟级**）。
- **可解面**：长关/多机关关的唯一现实路径；forest_15 尾段这类"±1f=±4px vs 带宽 ±5px"的像素带，段内机器扫参（10^4-10^5 候选）正好覆盖人工 30 候选穷尽后的剩余空间。
- **成本**：在 A 之上 +1-1.5 人日（检查点 JSON 格式 + 前缀重放/live-world fork）。

### C. MCTS（确定性仿真 + UCT）

- 理论契合（确定性 → 收敛保证），但本项目三重不利：深度 1500-8000 帧（UCT 需海量模拟才能穿透稀疏奖励）、无 value 网络引导、无状态克隆使每次模拟从根重放。段内短时程（~120f、分支 9）口径：5000 次模拟/决策点 ≈ 38s 单核 / 5.4s 池(7)，一关 30 决策点 ≈ **2.7min 池化/关**——可行但相比 B 无增益（B 用分段解决了 C 靠树深度硬扛的问题）。
- **结论：不作为主方案**；仅当未来引入学习价值网时重评。

### D. 强化学习（PPO 等）

- 仿真侧惊人地便宜：内核=完美确定性仿真器，7 核 ~110k 帧/s → 10^8 帧经验 ≈ **纯仿真 2.5h**。真正成本在：①JS 生态无现成 PPO，引 Python 栈（gym 桥接或内核 wasm 化）+ 训练调参 = **1-2 周工程起步**；②reward 塑形（x 推进+门距+钻石-死亡）对稀疏通关仍需课程学习，48 关通用策略更是分布泛化问题；③**产出形态与产线冲突**：策略是神经网络控制器，无法硬化成 ±1f 鲁棒事件表——即便录制成事件表也要回炉 optimize/MC，绕开不了真机鲁棒性问题。
- **结论：对 48 关规模过重，现在不做**。远期若做，先 behavior cloning（8+ 绿关事件表 = 免费示范数据）再进化微调，且只为"找骨架"不为"出路线"。

### E. 混合（**推荐**）

三层递进，每层独立可交付：

- **E1 机器粗搜**：A 方案（原语级 beam/GA）产出内核 WIN 路线 → 直进现有产线。"人给策略骨架"退化成"人给检查点"，人工介入从帧级降到里程碑级。
- **E2 机器精修增强**：现有 optimize（单事件 ±Nf 坐标下降）升级为**段级联合参数搜索**（CMA-ES/GA over 段内事件偏移向量，目标 = fatal 数/MC 失败数）——人工开环手段（整块平移、单参数扫描）已证明不够（forest_15：30 平移候选全 141 不动、D=86 孤立尖峰，note/evidence/forest_15/01号档:21；handoff.md:4），联合非线性扰动是明确的未覆盖维度。ScanPool/fatal 计数全部现成，**这是性价比最高的一步**。
- **E3 检查点自动提取**：geom 网格 + 机关事件门控自动生成候选检查点 → 全关零骨架搜索 → 批量产线。放批量期。

## 4. 约束与风险

1. **内核 WIN ≠ 真机 PASS（最大风险）**：真机是可变 dt 环境，CDP 派发每事件 0-5ms 抖动 + ~1/315 概率 40ms 离群 ≈ +2.4f 迟到（scripts/e2e/mc.mjs:4-7 实测口径；MC≥98% 才许进门禁，mc.mjs:7）。→ **搜索接受判据必须带鲁棒性项**：两阶段制——先裸 WIN 定骨架（快），再以"±2f 联合扰动全 WIN / MC 失败数"为目标硬化后收（每候选 ×5 回放，63µs/帧下可负担）；硬化期直接复用/增强 optimize+mc，不另起炉灶。
2. **双角色耦合**：逐帧联合 64 分支不可行；原语化后用 (a) 双序列基因（GA）或 (b) 交替规划（先 wg 冻 fb 再反哺）。botcore 的 `{fb,wg}` 双程序结构已验证 (a) 的工程形态；bot4 实战里"wg 等 fb 机关事件"（bot4-f05.mjs:142 `wait(p3East)`）证明跨角色同步谓词是好用的第三条路。
3. **算力与产线并发纪律**：8 vCPU VM 已按 55-70% 频率折价（ubuntu-server-profile.md:12）；产线 SOP 要求多 agent 并发时 --jobs≤4（route-synthesis.md）。**搜索是长时满载负载，必须 nice 后台 + 与真机门禁（route.mjs 可变 dt）严格错峰**——CPU 饥饿会污染门禁时序判定。内核搜索本身（headless 固定 dt）不受此污染，可随意并发。
4. **配额经济学**：舰队最大死因是 token 配额墙（handoff.md:11、archive-2026-10.md:7/29，两波全灭、单流 4-12.6h 湮没）。本地 CPU 搜索 0 token，是把"人工初排的 token 时长"置换为"CPU 小时"的结构性降险——但**搜索框架的开发调试本身花 token**，MVP 必须压缩在单槽 ≤2 人日、工具先行（本档 tools/ 已给出四个可运行基件）。
5. **搜索前提 = 内核下存在解**：forest_25 已 oracle 实机判死封印（e477c72），搜索对它无意义；机器搜索的负结果（穷举后不可解）本身是有价值的交付（挂起档的机器穷举附录），但别把算力烧在已被判死的关上。
6. **确定性边界**：搜索全部走缺省 simTimeS 风时基（=det 门禁口径，world.ts:69）；真机相位差异已被 MC 门禁模型覆盖，无需在搜索期另建模型。

## 5. 推荐路线图

### MVP（≤2 人日）：原语级 beam 搜索闭环

- 恢复 botcore（evidence → `scripts/e2e/routetool/botcore.mjs`，去 TEMP 相对路径）；
- 新增 `autosearch.mjs`：检查点 JSON（人填：x/y/机关 state/存活断言 + 段 horizon）+ beam 主循环（live-worlds，池(7)）+ 裸 WIN 后自动 toRouteDoc 落 routes JSON；
- 验收标准：**在任一已绿关（forest_01 或 forest_03）零人工重搜出 WIN 路线，且过 scan ±1f fatal≤个位数**（不要求 MC≥98%，那是硬化层的事）；实测脚本预算 ≤1 核小时/关。
- tools/microsearch.mjs 已验证核心闭环（54 evals/s，目标塑形下 5 层单调推进），MVP 是把它加粗：真原语库、双角色独立基因、池化。

### 二阶段（+3-4 人日）：段级联合硬化器 + 两个攻坚试点
